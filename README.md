# 采购标段截标时间核验工具

面向投标专员与招标站信息管理员的网页工具，包含两个相互独立的核验页面：

1. **截标时间核验**（首页）：输入公告列表页地址、项目编号、标段号，沿分页抓取原公告、延期公告和终止公告，按发布时间合并出该标段当前有效的投标截止时间。
2. **机读元数据核对**（`/metadata`）：输入公告目录 URL 和项目编号，沿同站分页读取单标段原公告详情，提取正文中的项目编号、标段号和截止时间，并与页面 JSON-LD `@graph` 中机读声明的 `bidDeadline` 逐标段核对，供管理员核查下游索引读到的截标时间是否与原公告相符。

应用使用 Python FastAPI，连同本地公告示例站通过 Docker Compose 启动。示例站为纯本地数据，**构建镜像后整个演示不需要访问互联网**。

## 启动

```bash
docker compose up --build
```

- 截标时间核验：<http://localhost:8000>
- 机读元数据核对：<http://localhost:8000/metadata>
- 本地公告示例站：<http://localhost:8001/notices?page=1>
- OpenAPI：<http://localhost:8000/docs>

首次启动会下载 Python 镜像与依赖；镜像构建完成后，核验、翻页、查看来源链接都在本机完成，可断网演示。

停止：

```bash
docker compose down
```

## 演示用例

首页已提供一键示例：

| 用例 | 项目编号 | 标段 | 预期 |
| --- | --- | --- | --- |
| 投标进行中（已延期） | `DEMO-2026-001` | `02` | 有效截止时间 `2026-11-12 09:30`，来源为第 2 页延期公告 |
| 已终止 | `DEMO-2026-001` | `01` | 状态“已终止”，**不显示有效截止时间**；时间线保留原公告、延期、终止三次变化及各自来源 |
| 不同编号格式 | `DEMO-2026-002` | `A` | 有效截止时间 `2026-11-25 14:00`；A 包的成交结果公告不改变截止时间 |

示例数据故意分布在第 1–4 页：`DEMO-2026-001` 的原公告在第 1 页，01 标段延期在第 2 页，终止在第 3 页；同项目 02 标段也有自己的公告，核对 01 标段时不会被混入。第 4 页是机读元数据核对专用的 `DEMO-2026-004` 样例。

示例站也可以在宿主机通过 <http://localhost:8001/notices?page=1> 直接浏览。工具内预填示例地址 `http://localhost:8001/notices?page=1`；即使应用与示例站分处不同容器，工具也能识别这个公开地址并转到容器内网抓取。核验结果中的所有来源链接会自动转成 `http://localhost:8000/demo/...` 代理链接，因此浏览器也可直接打开。

## 核验规则

1. **分页发现**：从列表页开始，沿 `rel=next`、分页器内的页码/下一页链接继续抓取，直到没有更多页或达到安全上限。
2. **精确匹配标段**：只有详情页中项目编号和目标标段号同时匹配才纳入合并。列表页有明确项目/标段信息时会先排除其他项目和其他标段，详情页仍会再次校验，避免混入同项目其他标段。
3. **按发布时间排序**：将命中的原公告、延期/更正公告、终止公告按详情页发布时间合并。
4. **只应用明确修改**：延期公告只有载明新的投标截止时间时才替换旧时间；页面只是引用旧时间、或只说“另行通知”而没有新时间时，结论为“无法判定”，不会把旧时间继续当作有效时间。
   - 同时支持“原时间……现延期至……”“……变更为……”“变更后：……”等写法，避免把“原时间”误当新时间，也不会把开标时间误当投标截止时间。
5. **终止优先**：一旦终止公告发布，状态固定为“已终止（不再接受投标）”，有效截止时间为空，旧时间只出现在历史时间线中并明确标注失效。
6. **失败即无法判定**：列表页、分页页、候选详情页抓取失败，详情页关键字段无法解析，缺少原公告，或相关公告缺少发布时间导致无法排序时，页面显示“无法判定”和失败/检索地址，并置空有效截止时间。**不会沿用之前的查询结果**。
7. **无缓存**：每次查询都实时重新抓取，不保存、不读取旧结论。

其他公告（如成交结果公告）可以出现在命中的公告列表中，但不会改变标段状态或截止时间。

## 机读元数据核对（/metadata）

信息管理员用它核查下游索引读到的截标时间是否与原公告相符。输入**公告目录 URL 与项目编号**即可，不需要指定标段号：工具会沿同站分页读取该项目各单标段原公告详情。

### 数据模型（JSON-LD `@graph`）

目录页与详情页都可以内嵌 `application/ld+json` 脚本块：

- **项目节点**：`@type: Project`，以 `projectNo` 标识项目，以 `hasPart` 中的 `@id` 引用标段节点；
- **标段节点**：`@type: TenderLot`，提供 `lotNo` 与 `bidDeadline`（ISO 8601 时间）。

标段节点通常只在详情页发布，项目节点在目录页通过相对/绝对 `@id` 引用它，因此必须跨页抓取后才能完成关联。`@id` 与 `hasPart` 引用均按所在页面 URL 解析。

### 核对规则

1. **跨页关联**：汇总全部目录页与详情页 `@graph` 中的节点，按 `@id` 建立索引；仅当项目节点的 `projectNo` 与输入项目编号匹配、且其 `hasPart` 能解析到同 `lotNo` 的标段节点，同时详情正文中解析出同项目编号、同标段号的截止时间时，才进行两侧时间比较。
2. **一致 / 差异**：机读 `bidDeadline` 与正文截止时间（按页面本地时钟，忽略时区偏移）相同记“一致”，不同记“差异”，两侧来源链接同时列出。
3. **冲突即待核**：同一标段 `@id` 在不同页面声明了互相冲突的 `bidDeadline`、`bidDeadline` 无法解析，或缺少可对照的正文时间时，该标段标“待核”。**即使其中一条机读声明恰好与正文吻合，也不会报一致。**
4. **悬空引用即待核**：`hasPart` 引用的 `@id` 在所有已抓取页面的 `@graph` 中都没有对应节点时，单独列为一条“待核”，保留引用值与项目节点来源。
5. **失败即本轮不完整**：目录页、分页页或详情页抓取/解析失败时，整轮标记为“不完整”：已确认的差异、待核项照常保留，但页面不会宣称“全部一致”。JSON-LD 脚本块本身格式错误只记提示并隔离该块，不影响同页其他数据的核对。
6. **无缓存**：每次查询实时重新抓取。

### 元数据演示用例

| 项目编号 | 预期结果 |
| --- | --- |
| `DEMO-2026-001` | 01、02 两个标段跨页关联后均“一致”，本轮完整 |
| `DEMO-2026-002` | A 包“一致”（结果公告不参与元数据核对） |
| `DEMO-2026-003` | B 包“一致” |
| `DEMO-2026-004` | D 包机读时间与正文不符（**差异**）；C 包同一 `@id` 两条 `bidDeadline` 互相冲突（**待核**，一条吻合也不报一致）；E 包 `hasPart` 引用无对应节点（**待核·悬空**） |

示例站共 4 页：`DEMO-2026-004` 的项目节点在第 4 页目录，C/D 标段节点在各自详情页，悬空的 E 节点没有任何页面发布。

### 元数据 JSON API

```bash
curl -G http://localhost:8000/api/metadata \
  --data-urlencode 'list_url=http://localhost:8001/notices?page=1' \
  --data-urlencode 'project_no=DEMO-2026-004'
```

也支持 `POST /api/metadata`，请求体为 `{"list_url": ..., "project_no": ...}`。

关键返回字段：

- `complete`：本轮抓取/解析是否完整；为 `false` 时不得宣称全部一致
- `summary`：`consistent` / `difference` / `pending` 三类行数
- `rows[]`：每个标段一行，含 `status`、`reason`、机读声明 `declarations`（带 `source_url`）、正文 `body`（带 `url`）、`project_id` 与 `reference_ids`
- `failures`：抓取/解析失败地址及阶段
- `graph_docs`：每个含 JSON-LD 的页面、节点数及解析错误
- `searched_pages` / `checked_detail_urls`：本轮检索范围

## JSON API

```bash
curl -G http://localhost:8000/api/check \
  --data-urlencode 'list_url=http://localhost:8001/notices?page=1' \
  --data-urlencode 'project_no=DEMO-2026-001' \
  --data-urlencode 'section_no=01'
```

也支持 `POST /api/check`：

```json
{
  "list_url": "http://localhost:8001/notices?page=1",
  "project_no": "DEMO-2026-001",
  "section_no": "01"
}
```

关键返回字段：

- `status`：`ongoing` / `extended` / `terminated` / `unknown`
- `determinable`：是否有足够证据形成结论
- `effective_deadline`：当前有效截止时间；终止或无法判定时为 `null`
- `deadline_source_url`：当前结论来源链接
- `changes`：按发布时间排列的变化记录，每条都带 `url`
- `failures`：抓取/解析失败地址及原因
- `notices`：命中的目标标段公告（不包含其他标段）

## 本地测试

不启动容器也可运行解析与合并规则测试（需要先安装 `requirements.txt`）：

```bash
python -m unittest discover -s tests -v
```

测试使用 `httpx.MockTransport`，覆盖跨页、延期替换、终止失效、同项目其他标段隔离、详情页失败、缺少原公告和“无新时间的延期”等场景；`tests/test_metadata.py` 另覆盖 JSON-LD 跨页关联、一致/差异、机读声明冲突、悬空引用、抓取失败不完整、坏 JSON-LD 隔离等场景。

## 边界与限制

- 只抓取 HTTP/HTTPS 的 HTML 页面；链接限定在输入列表页同一站点（scheme + host），不会跟随站外跳转。
- 单次查询设置列表页/详情页数量和响应大小上限，避免误抓大型站点；超过上限时结论为“无法判定”而不是猜测。
- 不处理需要登录、验证码、JavaScript 动态渲染的公告站。
- 日期按页面原始时区文本解析（示例为北京时间），不进行时区换算。
- 示例站数据均为虚构，不代表任何真实采购项目。
